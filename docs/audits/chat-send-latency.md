# HTTP 聊天发送延迟实测

日期：2026-11-14。决策见 ADR-059。前端基线提交 `85149da`，后端基线 `97b9835c`，两者均保留任务开始时已有及其他任务的工作区改动。

## 结论与定位

最终兼容实现的 HTTP 中位数从 **644.5ms 降为 554.5ms，下降约 14%**。正式消息广播确认中位数为 **516.5ms**；前端现在收到这份已落库实体便结束发送状态，比原来等待 HTTP 的中位时间缩短约 20%。没有达到百毫秒内发送，剩余耗时仍包括远程依赖访问，不能宣称性能问题已完全消除。

本地 Vite 5173 最初没有 API 覆盖，仍默认访问线上服务。当前本机 `.env.development.local` 已将 API origin 设为 `http://localhost:5173`，通过开发代理访问 8123 HTTP 与 8090 Netty 根路径。HTTP 代理返回 200，WS 握手及本人广播均已验证。配置仅在 development 模式加载，不写入账号或令牌；生产构建沿用部署配置。

后端当前启用 `pre` 配置，数据库与 Redis 均为远程地址。本次没有修改该配置或缓存登录、封禁、禁言、VIP 和积分。JDK 调用栈三次采样分别停在 Redisson 解锁、读取预留、写入预留，说明主要等待发生在通信链路。原定位调用还可能同步等待外部服务 5 秒，失败不缓存；现在私网地址直接跳过，公网冷缓存异步预热并对失败退避。

Redis 优化合并预留读取与全局递增 ID 生成，保留独立分布式锁以及写入前的七天 ID 预留、写入后的七天回执。最终版本继续使用原 Kryo codec 写入和读取预留，兼容已有回执；实测结果以这一版本为准。

## 测量方法与原始耗时

环境：Windows 本机、Node.js 25.8.1、JDK 8.0.504、已启动的 Spring Boot 服务；浏览器回归使用已安装 Chrome 157.0.8103.51。真实服务测试使用用户授权账号和专用合成消息，账号、令牌与真实聊天正文未写入测试源码、报告或截图。

使用单账号依次 POST `/api/chat/message/send`，从调用 fetch 前到完整 JSON 返回后以 `performance.now()` 计时；通过真实 WebSocket 只记录本次 clientMessageId 对应的广播到达时间。最终版本在 DevTools 重载后先预热一次，再连续采样八次；采样时浏览器矩阵回归已结束。API 直连 8123，最终广播通过本地 Vite WS 代理接收。Redis、数据库和落库流程均真实执行，没有 mock。
