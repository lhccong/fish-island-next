# 发送红包验收

日期：2026-11-13。环境：Windows 本机、Vite 开发服务、Playwright Chromium。使用合成账号、消息与响应，没有实际消费生产账号积分。

## 范围与行为

- 聊天工具栏新增 44px“发红包”入口，普通/拼手气/答题共用表单和当前主题控件；橙金预览复用已有红包变量。手机使用单列，标题、关闭、反馈和操作固定，正文使用 reserved ScrollArea，文本输入 16px 且不因输入框 Enter/输入法提交而直接创建。
- 创建通过旧版 POST `/api/redpacket/create` JSON；权限、当日次数及余额以服务端响应为准。前端检查整数积分、份数和答题内容，不虚构余额。普通/拼手气请求不携带答案，聊天仅发送红包 ID 标记。
- 创建与发布分别确认；同一创建请求互斥，创建成功后发布失败只重试相同红包和 clientMessageId，不再次创建。聊天列表的原有重试同样驱动弹窗状态。收到消息确认后才展示发送成功；“再发一个”仅重置表单，不隐式提交。
- 关闭保留当前账号表单和进行中的请求；账号切换取消并隔离状态。主题/明暗切换不新增请求、不重连、不丢失普通聊天草稿与答案。网络、系统错误或无效响应导致创建结果未知时不提供无条件创建重试，明确提示核对积分记录或联系管理员。

## 验证

测试：`tests/e2e/chat-red-packet-send.spec.ts`，配置：`playwright.chat-red-packet-send.config.ts`。

矩阵：WPS 表格、微信绿、企业微信、飞书蓝、钉钉蓝 × 明亮/暗夜 × 桌面 1280×720、375×812、390×844。

覆盖初始表单/空值/校验、拼手气/普通/答题创建、业务拒绝、创建中关闭后恢复、发布失败后复用消息重试、确认成功、再次创建、未知结果锁定、答案与普通草稿保留。选择器检查触屏选项与边界，弹窗检查 Esc/关闭与焦点返回；正文检查真实触屏拖动、桌面滑轨显示和手机隐藏、至少 24px/20px 末端 gutter、4px 起始/顶部留白、输入聚焦及内部无横向溢出。截图抽查手机和桌面的明暗布局。

最终矩阵 **30/30 通过**（4 workers，约 3.4 分钟），另补验 WPS 明亮桌面的焦点环留白，1/1 通过。原始问题修复包括：成功态“再发一个”切回提交态时明确阻止该次点击触发表单默认提交；文本字段焦点环采用 2px + 2px，完整落在预留空间内；触屏拖动绑定正文 gutter，避免误将多行题目输入框自身的滚动当成正文滚动。

`npm run check` 整条通过：Prettier、零警告 lint、TypeScript、52 个测试文件 / 211 项单测、生产构建均通过。构建仅保留原有人生重开大分块提示。创建相关专项单测覆盖表单规则、HTTP 协议、互斥/取消/未知结果、队列满恢复和相同 clientMessageId 发布重试。
