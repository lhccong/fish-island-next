# 聊天性能与验收规范

以下是开发预算和验收目标，不是初始化阶段的测量结论。基线设备、浏览器版本、网络和数据集随报告记录。

## 1. 实现约束

- 页面只组合；输入、列表、消息行、会话摘要独立更新。
- 消息行按 ID 精确订阅，列表只订阅该会话 ID 序列；不能让输入或弹窗更新广播到所有消息行。
- 使用 react-virtuoso 处理变高行；key 稳定；尽量稳定组件类型与回调，禁止每次渲染创建新的列表 Header 组件类型。
- 上翻历史保持锚点；只有用户位于底部附近或主动发送时跟随新消息。离开底部时显示新消息提示，不强行跳底。
- 图片尽可能预留宽高/比例，懒加载并限制解码尺寸，加载完成不能抖动或反复强制 scrollTo。
- 文本解析按消息内容版本缓存；代码高亮、截图、表情数据动态加载。先测量，再决定是否使用 Worker。
- 高频入站消息短窗口批量提交；不可丢事件；后台页节流要配合有界队列与恢复机制。
- 历史分页建议初始 50 条，当前会话内存初始预算 1000 条；逐出远端页时保留游标与锚点信息，用户回看再加载。发送中/失败/当前引用等需要保留的数据应单独固定。
- 会话缓存设置 LRU 上限，登出释放；虚拟列表只限制 DOM，不自动限制消息缓存。
- 动画只用于必要交互；不为全部消息挂载布局动画、全屏模糊或持续运行的 JS 动效。

## 2. 可复现验证场景

使用发布构建 `npm run build` + `npm run preview`，避免将 React 开发模式/StrictMode 数字当作发布结果。

| 场景           | 数据与操作                                | 目标                                   |
| -------------- | ----------------------------------------- | -------------------------------------- |
| 长历史         | 服务端或夹具含 1 万条消息，分页加载与回看 | DOM 与内存符合窗口策略，历史锚点稳定   |
| 边输入边收消息 | 连续 60 秒，每秒 20 条文本消息并持续输入  | 不丢消息；输入到下一帧呈现 p95 < 50ms  |
| 突发           | 1 秒内接收 200 条消息                     | 不重复、不丢失，分批处理且输入可响应   |
| 混合消息       | 长文本、图片、链接、撤回及失败重试        | 图片加载后不跳动；无连续长任务         |
| 会话切换       | 多次切换后让旧请求返回                    | 不串会话、不重复订阅，草稿保留         |
| 断网恢复       | 离线、重连、补拉和服务器重复投递          | 去重正确；无补拉协议时明确限制         |
| 换肤           | 接收消息时切换皮肤与外壳                  | 不重连、不清空草稿、不丢消息           |
| 长时间运行     | 反复切会话/弹窗/连接，持续至少 30 分钟    | 无持续增长的监听器、定时器、DOM 和缓存 |

60Hz 基线设备的滚动目标是接近 60fps；记录掉帧和超过 50ms 的主线程任务，不能只看平均 FPS。输入延迟应通过统一 Performance 标记/浏览器 trace 测量并保留方法。

## 3. 体积预算

- 最小聊天入口的首屏同步 JS 暂定 gzip 总计 ≤ 200KiB；不包含延迟加载资源。预算需在真实聊天入口实现后验证，不能拿初始化页替代。
- 表情数据、Markdown/高亮、截图、管理后台、游戏不得进入最小聊天首屏。
- 构建默认打印的单文件 gzip 大小不是入口依赖总和；报告同时列入口、同步依赖、异步块与加载链。
- 超预算先分析依赖与拆包；确需调整时给出测量与 ADR，不为了指标破坏必要交互。

## 4. 每次报告至少记录

提交标识、发布/开发模式、机器与浏览器、数据集、测试步骤、trace/截图位置、体积、输入 p95、长任务、内存趋势、发现的问题及限制。没有测量就标记“未验证”。
